## 0. What changed since the private measurement

Re-running the tool against real, public repositories — not just the private one it
was designed against — is what this document is for, and it did its job: it found a
genuine resolver defect that the private measurement never exercised.

1. **The Vite query-suffix gap** (the reason this branch exists). `./app.css?url` and
   `~/app.css?url` (a Vite resource-query modifier) made `probe` search for a file
   literally named `app.css?url`, which never exists. Fixed by stripping a trailing
   `?…` (and a `#…` fragment, the same class of problem) once, centrally, in
   `resolve`, before any resolution rule runs — see `crates/kog-graph/src/extractors/typescript.rs`,
   `strip_query_suffix`. Six new unit tests. Effect on documenso: the four `?url`
   specifiers move from `unresolved` to `excluded` (they're CSS, not TypeScript
   source — `excluded` is the correct category for "resolves to a real file
   deliberately out of scope", not a resolver failure). This barely moves documenso's
   rate (§4), but *correctly categorised* is the entire point of this project.

2. **A second, unrelated defect, found by the same process.** Independently
   verifying the categorisation of every gap below (§6) — rather than trusting that
   "the tool is correct" — turned up a second resolver bug: on TanStack Query's
   `packages/svelte-query`, `createBaseQuery.svelte.ts` imports `./containers.svelte.js`
   (Svelte 5's runes-file convention: an explicit ESM `.js` specifier pointing at a
   `.ts` file, exactly like the existing `./b.js` → `./b.ts` fallback rule already
   handled — except the file's own name already contains a `.`). `probe`'s fallback
   stripped `.js` via `Path::with_extension("")`, then re-added a candidate extension
   via a second `with_extension` call — but `containers.svelte`'s own
   `Path::extension()` is `svelte`, so the second call replaced `.svelte` too,
   producing `containers.ts` instead of `containers.svelte.ts`. Fixed by trimming
   exactly the matched suffix's byte length instead of relying on `with_extension`
   twice. One new unit test, reproduced failing before the fix, passing after.
   **Effect: 25 of query's 33 `unresolved` diagnostics were this bug, not generated
   code.** Rate moves from 0.9776 (with the bug) to 0.9946 (fixed) — see §4 and §6.

Both fixes are proven with unit tests in `crates/kog-graph/src/extractors/typescript.rs`
and are part of the commit measured above. Every figure in this document was
generated by running the fixed binary once, end to end — nothing below was hand
corrected for either bug.

## 1. Reproducing the clones

```bash
git clone --depth 1 https://github.com/documenso/documenso.git bench/documenso
git clone --depth 1 https://github.com/TanStack/query.git bench/query
```

`--depth 1` is deliberate, not just fast: it guarantees the tree you scan is a
*fresh* clone, with no generated artefact left over from a previous `pnpm install`,
`prisma generate`, or build. That's the condition this document's categorisation in
§6 depends on — every "generated, absent from a fresh clone" claim below was verified
against a tree that has had exactly `git clone --depth 1` run on it and nothing else.

## 5. Rate arithmetic

```
resolution_rate = resolved / (specifiers_internal - excluded)

documenso:  10101 / (10346 - 16)  = 10101 / 10330 = 0.9778315585672798
query:       1462 / (1588 - 118) =  1462 / 1470   = 0.9945578231292517
```

Independently verified via `jq` on each `graph.json`:

```
$ jq -r '.stats | "\(.resolved) / (\(.specifiers_internal) - \(.excluded)) = \(.resolution_rate)"' documenso-graph.json
10101 / (10346 - 16) = 0.9778315585672798
$ jq -r '.stats | "\(.resolved) / (\(.specifiers_internal) - \(.excluded)) = \(.resolution_rate)"' query-graph.json
1462 / (1588 - 118) = 0.9945578231292517
```

**A reader's first suspicion on seeing a rate this close to 1.0** is that the
denominator was hollowed out by moving genuine failures into `excluded`. It wasn't:
on documenso, `excluded` removes 16 of 10,346 internal specifiers from the
denominator (0.15 %); on query, 118 of 1,588 (7.4 % — higher, because query's
examples import real `.vue`/`.svelte`/`.css`/`.json` files and real symlinks far more
than documenso does). §6 itemises every one of both counts by hand, cross-checked
against the filesystem, not merely trusted because the tool says so.

## 6. Categorised breakdown of every gap on both repositories

This is the section that matters. A rate this high invites the question of whether
the remainder is hidden failure. It is not — but showing that, one specifier at a
time, is the entire reason to publish this document rather than a bare number.

Method: `jq -r '.stats.diagnostics[] | "\(.kind)\t\(.specifier)\t\(.path)"'` on each
`graph.json`, grouped by hand, then each group's target checked against the actual
filesystem (`ls`, `readlink`, `cat` on the generating script or config) — repeated
independently for this document, not copied from an earlier analysis. §12 records why
this has to be done by hand.

| Group | Count | Generator |
| --- | ---: | --- |

because it is a distinct failure mode (a config file failing to load, not a
specifier failing to resolve).

## 11. Reproducing these figures

```bash
git clone --depth 1 https://github.com/documenso/documenso.git bench/documenso
git clone --depth 1 https://github.com/TanStack/query.git bench/query

cd kog   # this repository
export PATH="$HOME/.cargo/bin:$PATH"
cargo build --release

# documenso
time ./target/release/kog scan ../bench/documenso -o /tmp/documenso-graph.json
jq -r '.stats | "rate=\(.resolution_rate)  internal=\(.specifiers_internal)  resolved=\(.resolved)  unresolved=\(.unresolved)  excluded=\(.excluded)  external_distinct=\(.external_packages_distinct)"' /tmp/documenso-graph.json
jq -e '.stats.resolution_rate >= 0.95' /tmp/documenso-graph.json >/dev/null && echo "GATE PASSED" || echo "GATE FAILED"
jq -r '.stats.diagnostics[] | "\(.kind)\t\(.specifier)"' /tmp/documenso-graph.json | sort | uniq -c | sort -rn

# query
time ./target/release/kog scan ../bench/query -o /tmp/query-graph.json
jq -r '.stats | "rate=\(.resolution_rate)  internal=\(.specifiers_internal)  resolved=\(.resolved)  unresolved=\(.unresolved)  excluded=\(.excluded)  external_distinct=\(.external_packages_distinct)"' /tmp/query-graph.json
jq -e '.stats.resolution_rate >= 0.95' /tmp/query-graph.json >/dev/null && echo "GATE PASSED" || echo "GATE FAILED"

cargo fmt --all --check
```

## 12. What this measurement does not prove

- **Two repositories is not a corpus.** documenso and query were chosen for being
  public, real, and structurally different from each other (a Turborepo application
  monorepo vs. an Nx/pnpm library monorepo) — not sampled at random from any larger
  population. A rate this high on both says something about resolver correctness on
  these two shapes; it says nothing about how it generalises to a codebase with, say,
  heavy dynamic `import()`, CommonJS `require()` throughout, or a Bazel monorepo.
- **Both are TypeScript.** Same limitation as the document this one replaces: v0
  supports one language, and both measured repositories exercise only that language.
- **File granularity, not symbol.** An edge says two files are connected by an
  import; it says nothing about which symbol, of however many a file exports, is
  actually used.
- **The reason for each exclusion is still not recorded in `graph.json`.** `Stats`
  distinguishes `excluded` from `unresolved`, but not *why* — gitignored? a symlink
  the walker didn't follow? an unclaimed extension? Every categorisation in §6 was
  produced by hand: grouping diagnostics by specifier shape, then checking each
  group's target against the real filesystem (`ls`, `readlink`, reading the
  generating script). **It is not regenerable from `graph.json` alone.** This is the
  same gap the roadmap's v0.1 line item ("record *why* each specifier was excluded")
  exists to close, and it is exactly as true here as it was in the document this one
  replaces — two measurements later, the categorisation is still not something a
  reader can reproduce with `jq` alone, only by redoing the by-hand filesystem check
  this document did.
- **The 37 symlink exclusions on query (§6.4) were verified by pattern, not one by
  one.** All 37 share the same two target names (`root.eslint.config.js`,
  `root.tsup.config.js`) and the same `../../` relative-symlink shape; one of each was
  checked by hand (`readlink`, `realpath`), and the total count was cross-checked
  against `find . -type l | wc -l` (37, exact match) — but not all 37 individual
  symlinks were dereferenced and confirmed one at a time.
- **A rate in the high 0.9s on two runs is two data points, not a distribution.**
  Each repository was scanned once for the figures in §3–§6; no average, no variance,
  no regression test beyond the unit tests in §9 accompanies either number.
