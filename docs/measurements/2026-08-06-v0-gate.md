## 0. What changed since the first measurement

The first version of this document (commit `390ee81`, completed on `3a7ded3`) went
through a full branch review before merge. Two fixes potentially touched the figures
below:

1. **`external_packages_distinct` was counting specifier strings, not packages** —
   `next`, `next/link`, `next/navigation` counted as three distinct packages instead
   of one. Fixed by collapsing to the package name (`@scope/name` or first segment) at
   resolution time. Measured effect on the acceptance target: **95 → 77 distinct
   packages** (§4), which finally aligns the published figure with the one measured by
   hand in design §3.4 (77). On `lueur`: 25 → 24.
2. **A file the tool itself fails to read or parse was falling into `excluded`**
   instead of `unresolved`, which would have let the published rate stay at 1.0000
   while a broken extractor failed silently. Fixed to count this case in `unresolved`.
   **No numeric effect on this document**: `mastore-saas` contains no file the tool
   fails to read or parse (`files_parsed == files_discovered` already, both before and
   after), so there is nothing to recount here. The fixed behaviour is proven by two
   synthetic unit tests (`crates/kog-graph/src/graph.rs`), not by this document — see
   the fix report for the break/rerun/restore proof.

A third fix touches only the documentation, not the binary: the rate formula in the
design doc (`docs/design/v0-design.md` §5) said `resolved / specifiers_internal`,
while the code — and this document, from its first version — compute
`resolved / (specifiers_internal - excluded)`. The design doc was corrected to
describe what the code actually does; this document did not have that error and so
did not change on this point.

All figures below were **regenerated by rerunning the binary** on the commit measured
above, not recopied or hand-corrected.

## 5. Rate arithmetic

```
resolution_rate = resolved / (specifiers_internal - excluded)
                = 3160 / (3211 - 51)
                = 3160 / 3160
                = 1.0000
```

Independently verified via `jq` on `graph.json`:

```
$ jq -r '.stats | "\(.resolved) / (\(.specifiers_internal) - \(.excluded)) = \(.resolved / (.specifiers_internal - .excluded))"' saas-graph.json
3160 / (3211 - 51) = 1
```

**On this first suspicion a reader might have** — a rate of exactly 1.0000 invites
the question of whether the denominator was hollowed out. It wasn't: `excluded`
removes 51 specifiers out of 3211 from the denominator, i.e. 1.6 %, a small fraction
and fully itemized below. It overlaps with no `unresolved` — there are none on this
scan — so nothing was "moved" from a category that would have lowered the rate into
one that spares it. The 51 exclusions are, one by one, imports to real files located
outside the scanned tree (see §6), not resolver failures in disguise.

A second suspicion, specific to this revision: the branch review precisely found that
a file the tool fails to read or parse could, before the fix, be classified `excluded`
instead of `unresolved` — which would have let this figure stay at 1.0000 even with an
extractor broken on hundreds of files. That is not the case here: `files_parsed` (727)
equals `files_discovered` (727), so no file fails, so this mechanism is not exercised
by this measurement. The fix itself is proven only by the synthetic unit tests added
in `graph.rs` (see the fix report for the break/rerun/restore proof), not by a figure
in this document — that is precisely the limitation documented in §12: a single
project, with no broken file, cannot exercise this path.

## 12. What this measurement does not prove

- **Only one project measured for the rate.** Criterion 1 rests on `mastore-saas`: a
  single monorepo, admittedly chosen for its difficulty (Turborepo, five nested
  tsconfigs, `extends` chains, workspaces). A rate of 1.0000 on this project says
  nothing about how it generalizes to a TypeScript project structured differently
  (heavy dynamic imports, pure CommonJS `require()`, an Nx or Bazel monorepo, etc.).
- **Only one language.** TypeScript/JavaScript only. The design (§3.2–3.3) is
  explicit: every language must clear its own resolution gate; Go and Swift are not
  measured here and therefore have no resolution figure to date.
- **File granularity, not symbol.** The graph says nothing about what, inside a file,
  depends on what. Two files linked by an edge may share only one symbol out of fifty.
- **A rate of 1.0000: a single data point, not a guarantee.** A single run was timed
  and read per run (two runs total for this revision); no average, no regression test
  accompanies this figure beyond the repository's unit tests (§9). A perfect rate on
  this specific project does not predict behaviour on a project with different
  conventions.
- **The "broken file counted against the rate" fix is not exercised by this
  document.** `mastore-saas` contains no file the tool fails to read or parse, so this
  measurement cannot show the rate drop under the effect of this fix — only the
  repository's synthetic unit tests show it (§0, §5).
- **The reason for each exclusion is not recorded in `graph.json`.** `Stats`
  distinguishes `excluded` from `unresolved`, but does not say *why* a given specifier
  is excluded (gitignored? a directory always excluded? an unclaimed extension?). The
  categorization table in §6 was produced by hand, by inspecting the filesystem and
  `.gitignore` — it is **not regenerable from `graph.json` alone**. Given that
  "measured, itemized and reproducible" is the design's central argument (§2), this is
  a limitation that deserves to be stated explicitly rather than discovered by a reader
  trying to redo the §6 table with `jq` alone.
- **Visual rendering: no error, no smoothness measurement.** This revision verified,
  in a real browser, that the graph loads and renders with no console error and with
  the correct figures (§7–8). It did not measure perceived smoothness on pan/zoom
  (frame-rate profiling under interaction), which remains a qualitative claim.
- **The 51 exclusions were not verified one by one by hand**, only by group and by
  sample (paths checked by hand for one representative of each group, §6). An isolated,
  misclassified exclusion would remain possible in theory, even though the structure of
  the paths (all under `generated/prisma`, `.next/`, or an asset extension) makes that
  unlikely.
